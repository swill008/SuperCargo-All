## Job rules (user, 2026-10-14)

These are the intended behaviour of Other mode. Change them only with the user.

1. **Haul mode is only for hauling.** In Haul mode the Other side ignores every contract; it never creates jobs.
2. **Two outcomes:** completed or abandoned. Fail, Abandon and "Player left" all count as abandoned; the reason is not shown.
3. **The latest ending wins.** Endings in the log (EndMission Complete / Fail / Abandon) mark the job automatically during play.
4. **Re-share reactivates.** A new "Contract Accepted" for a mission id makes its job active again, even if it was archived (a party member re-shared it after you left).
5. **Quitting ends contracts.** "Player requested disconnect" (quit to menu, server hop) and `<SystemQuit>` with `Quit via console command` or `User closed the application` (quit game) mark every active log job abandoned.
6. **A crash keeps jobs.** No ending is inferred from missing contracts: not at app start-up, not from a new Game.log, not from a log scan. After a crash you rejoin with your contracts, so jobs stay active until the log ends them or you do.
7. **Start-up replays only new log events** (after `lastLogEventAt` + `lastLogEventCount`, so nothing is applied twice): the previous log in `logbackups` when newer than the watermark, then the current Game.log. A previous log that ends with SystemQuit applies rule 5; one that ends without it is a crash (rule 6). REFRESH (rule 26) is the only re-read that ignores the watermark, and it applies markers only.
8. **One window owns Other.** Only the main window applies log events and saves; the overlay shows the same jobs, sends its button presses (step done, complete, abandon) to the main window, and reloads when the main window saves.

## Where the player is (user, 2026-10-14)

9. **One `where` field.** The jobs doc (`other-jobs.json`) keeps the player's position as `where: Where | null` (`src/other/otherWhere.ts`: name, label, point, system, body, `source`, `at`). It replaces the old `currentLocation` / `currentLocationAt`. Sources:
   - `tick`: you tick a step DONE / GO HERE / TURN IN → that step's place (read before the tick changes the active step);
   - `objective`: an Objective Complete line in the log ticks a step → that step's place, at the log time;
   - `inventory`: the log's RequestLocationInventory / Update Inventory Location events (a "left the place" event clears `where` only when the current `where` came from `inventory`);
   - `map` / `displayinfo`: WHERE AM I (rule 11);
   - `typed`: the STARTING AT box (stored separately as `startLocation` + `startTypedAt`).
   Quantum and ATC lines are **not** a source: no log line names the place (checked against real logs). The UI shows which source the start came from.
10. **STARTING AT mode** (`otherStartMode`, AUTO / FIXED toggle on the start line). **auto** (default): the newest of the typed start (`startTypedAt`) and the latest clue (`where.at`) wins. **fixed**: the typed start only; empty means no start. A non-typed start older than 5 minutes shows as stale.
11. **WHERE AM I** reads the star map: hotkey `otherWhereHotkey` (default Ctrl+Shift+L) or the one button on the overlay card's start line. One screenshot, two zones: zone 2 (r_DisplayInfo 3 text, upper right) first when `otherWhereUseZone2`, then zone 1 (the map's bottom location line) as fallback. The result is broadcast to every window; only the main window applies it (`applyWhere`) and saves. A failed read (hotkey or button) shows "couldn't read the map, try again" and changes nothing; a second run while one is running returns busy.
12. **Location never touches the log watermark.** `where` updates (from any source, including WHERE AM I) never change `lastLogEventAt` / `lastLogEventCount`; only log job events advance them (rule 7).
13. **Distances are system-aware.** A stop in another system goes via the gateway ("38.0 Gm + 1 jump"); stops sort by jumps, then metres. Two points on the same planet or moon are measured over the surface ("≈490 km surface").

14. **Position accuracy (0-10).** Every clue carries `where.accuracy`, set when it is taken (`ACCURACY` in `otherWhere.ts`): display info near a body 10, display info in space 9, map line naming a place 8, inventory 7, objective 6, tick 5, map line naming only a body 4, map coordinates only 3. A typed start has no score (it is the user's choice). The overlay start line shows a coloured `ACC n` tag with a 10-segment bar; the Next tab shows the score and its word (exact 10-9, good 8-6, rough 5-4, guess 3-1, none 0) on a small red-orange-green slider under STARTING AT. Number and word are always shown, so colour is never the only signal.
15. **Fading.** The score drops by 1 for every 5 minutes since `where.at`, never below 1 (`whereAccuracy()`). A display-info read whose ServerTime differs from the PC clock by more than 2 minutes is "maybe stale": −3 (min 1), noted in its checks and diagnostics.
16. **The whole panel is read.** Zone 2 reads the whole r_DisplayInfo panel and uses, best first, the planet zone line or CamPos + the body centre (near a body), then the SolarSystem line (checked against Root; in space only, rule 32), then zone 1, each only when its sense checks pass (recorded in `checks`). A read with no system named is still OK. After every WHERE AM I read the overlay shows a short note for about 4 s ("Read OK · display info · ACC 10", "Panel unreadable → used map line · ACC 3", or the failure message; the previous start is kept on failure).
17. **Live reads** (`otherWhereLive`, off by default; `otherWhereLiveSec` 45, 30-120): the main process re-reads zone 2 only, every N seconds, with no keypress; it skips while a read is running or a hotkey is being recorded. Only good reads change `where`; live reads are silent, except one quiet message after 3 failures in a row. Diagnostics count them.
18. **Tracked mission.** The panel's `Tracked mission : <name> [<uuid>]` line marks the active job whose mission id starts with the same first 8 hex characters (O/0 and I/1 tolerated) as `trackedMissionId` in the doc. The overlay shows a TRACKED tag on that job and jumps the card to its next stop when a new tracked id arrives; the Next tab shows the tag too.
19. **AFK button** (overlay, next to TURN IN / ABANDON; Windows only). Click to start, click again to stop; while on it is amber with "AFK ON · next key in N s". Every `otherAfkIntervalSec` (15 s) it brings the Star Citizen window to the front and presses `otherAfkFirstKey` (F2, the map) on the first cycle, then `otherAfkCycleKey` (F1) each later cycle, as scan codes through Windows SendInput (a PowerShell helper; no native module). It stops on the button, when the game window is gone, after `otherAfkMaxMin` (120; 0 = no limit), or when the app quits, and leaves the game focused. With `otherAfkWhereRead` on, it takes a quiet WHERE AM I read about once a minute, ~2 s after a key press. On other systems Start returns "Windows only". The settings hint says: "Presses keys in Star Citizen for you. Check RSI's terms before using it; the game window is brought to the front every cycle." Test seam: `SC_AFK_DRYRUN=1` sends no focus or keys and only records the presses (`presses`, `lastKeys`); `SC_AFK_INTERVAL_MS` sets the interval in a dry run.
20. **Hotkey recorder.** Both global hotkeys (OCR capture and WHERE AM I) are set by clicking the field and pressing the combination ("Press keys…"); Esc cancels, Backspace/Delete clears (off). A combination needs Ctrl, Shift or Alt unless it is F1-F24; modifier-only presses are ignored. While recording, all app global hotkeys are paused. It warns about a clash with the other hotkey or Ctrl+Shift+D (debug), and after saving shows "in use by another app" when registration fails.

## Places from mission markers (user, 2026-10-14)

21. **Body-frame markers.** A mission marker (`CLocalMissionPhaseMarker::CreateMarker`) gives a position in its zone's frame. A zone is calibrated as before (root zone, small zone, or a z-match with a UEX place). When it isn't, and the marker is not root or small, the zone may be a planet or moon's own frame: each body's radius is estimated as the median distance of its roster places (`Location.body`) from its centre (the roster entry named after the body); the candidates are bodies whose radius is within ±3% of |position|; for each, centre + position must land within 10 km of one of that body's places. Exactly one body passing → the zone is calibrated with that body's centre (method `body`, the near place recorded). None, or more than one (Hurston and microTech are both ~1000 km), → the zone stays uncalibrated and the decide trace says why. Calibration uses the merged roster (Haul + Other places, `mergeLocations`).
22. **Generic place names say where they are.** A step whose place isn't in UEX ("Security Compound") but whose point came from a marker carries `near` = the nearest roster place within 25 km. The overlay start/stop line and the Next tab show "Security Compound · near HDPC-Cassillo (4 km)" with the distance, instead of "Not found in UEX". A step whose pickup is still open is measured from its pickup place, never from its marker (rule 30).
23. **Zone tables are per server.** Zone ids change with every server (the same SolarSystem has a different id the next session), so the marker zone table for the current build is cleared on a new session line ("Log started") and on a disconnect or quit. Markers after that are calibrated fresh. Positions already placed on steps (system frame) stay. The decide trace records `marker zones reset: session` / `disconnect` / `quit` with the number of zones dropped.
24. **Pickup before delivery.** The next open step, and the step order the Next tab uses (show-all and route), put an open pickup before the open turn-in / delivery steps of the same job that carry the same item (case-insensitive), even when the game lists the delivery first. If either side has no item, game order is kept. Combined "collect from A, deliver to B" steps (`pickupLocation`) are unaffected. The saved steps keep game order.
25. **Export diagnostics copies to the clipboard.** After a successful save from the Settings or Debug button, the main process puts the whole saved text on the clipboard. The result line reads "Saved and copied · 1.4 MB · <path>", adding " (large: attaching the file may work better)" above 1 MB, or "Saved (copy to clipboard failed)". The `--export-diagnostics` command line never touches the clipboard.

## REFRESH (user, 2026-10-14)

26. **REFRESH re-reads markers for active jobs.** The REFRESH button (Next screen next to STARTING AT, Jobs screen header; not on the overlay) does three things: (1) main re-pulls the Other places roster (`otherPlaces:refresh`) and the renderer reloads it, so views recompute; (2) main re-reads the same files as the start-up scan (newest `logbackups` file, then Game.log) **ignoring the watermark**, and returns only `marker` events whose mission id is in the given list of active jobs, plus `session` lines for the build and zone context, in log order (`otherJobs:refreshScan`, `scanMarkersFor()`); nothing else (no accepts, objectives, endings, quits); (3) the main window empties the current build's zone table, calibrates again from those markers (`calibrateZone`, including the body-frame path) and re-places steps over all jobs. Why: marker lines are written when the contract is accepted, so after a restart the start-up scan (rule 7) never shows them again, and a step that a newer build could place (rule 21) stayed "Not found in UEX" (the user's J74).
27. **REFRESH never moves the watermark or revives jobs.** It does not change `lastLogEventAt` / `lastLogEventCount`, job status, steps' done flags, history, and never creates or ends a job; an ended job's markers are not read (only active mission ids are sent). Only the main window applies it (rule 8); the overlay has no button. The result shows on the screen for about 6 s and goes to the decide trace (`refresh`) and the debug log: "Refreshed · 1 job · 1 place found (Security Compound near HDPC-Cassillo)" or "Refreshed · nothing new" (counts: active jobs, markers read, steps that gained a position, zone result).
28. **Automatic once per version.** On the first start after an update (app version + git commit from DebugInfo differs from the doc's `refreshedForVersion`), steps 1-3 run silently after the start-up scan and the doc stores `refreshedForVersion`. Later starts of the same version don't run it (decide trace `auto refresh: new version`, once).

## Pickup distance and bad reads (batch 6, user 2026-10-14)

The case: standing at Covalex Distribution Centre S1DC06 (Hurston), job J82's combined step "Collect Scrap from Covalex Distribution Center S1DCO06 on Hurston. Deliver Scrap to Security Compound" (OCR doubled O) showed "≈4 km" and "near Covalex S1DC06 (4 km)": the pickup name matched nothing, so the row used the step's marker, which is the drop-off (Security Compound, ~4 km away). Two reads at the same spot said "Open space" and one said "Rappel · 46.4 km".

29. **OCR doubled zeros.** (Batch 7: folded into `placeKey`, rule 34.) Place lookup (`findRosterLocation`, `explainPlaceLookup`) tries, after exact and contains, a last tier on folded names with runs of two or more zeros collapsed to one inside words that carry a digit ("S1DCO06" = "S1DC06"), exact match only, with the same pick rules (coordinates first, address system). The lookup explains it as method `folded`.
30. **A pickup is measured from the pickup place.** (Batch 7: kept by the resolver, rule 35: a pickup has no marker.) While a step's pickup is open (`stepIsPickup`), its distance and `near` come only from the pickup place; the step's `position` (the marker) is never used, because on a combined collect-and-deliver step the marker sits on the delivery place. A pickup place that can't be found gives no distance (the row's no-distance text), not the drop-off's. After the pickup is done, the marker is used as before (rule 22).
31. **Unknown system names are not systems.** In display-info reads, `knownSystem()` returns '' for a name that is not a known system (garbled reads such as "Zone", "Zope"), so the read has no system rather than a made-up one; the map line keeps its title-cased name. Near a body, the body is looked up in the read system's places first, then in every system (a misread system name).
32. **Near a body, never the star-frame lines.** When the panel says the player is near a body (planet zone line or CamPos) but the body position fails (no body, or a failed check), the read gives no position: the SolarSystem / Root lines turn with the planet and don't match roster places. Its checks record `position: near <body> but the body position failed: star-frame lines not used on a planet`, and the previous start is kept (rule 16). In space the SolarSystem / Root path works as before.
33. **COPY TEXT / COPY IMAGES.** After a successful export from Settings or Debug, a COPY TEXT button (and COPY IMAGES, only when pictures were saved) sits next to the result line. COPY TEXT reads the last saved `.txt` back and puts it on the clipboard ("Text copied · 1.1 MB"); COPY IMAGES puts one picture on the clipboard: every saved picture side by side, top-aligned, 16 px black gaps, unscaled, saved next to the export as `<base>-all.png` and listed in `## IMAGES` as "saved: <base>-all.png (all pictures in one)" ("Picture copied (3 in one)"). Feedback shows for about 4 s; before any export both answer "no export yet". The automatic text copy on export (rule 25) stays.

## One stop-place resolver (batch 7, user 2026-10-14)

Why: a stop's place used to be found by a chain of rules (exact, contains, O/0 fold, zero fold, marker fallback, nearest place, pickup exception); each fix added a link and the links interacted (the J82 pickup got the drop-off's 4 km). One resolver now weighs all the evidence and returns one answer per stop, read by every screen, the route sort and diagnostics.

34. **One normaliser, one resolver.** `src/other/otherResolve.ts` (pure): `placeKey(text)` lower-cases, strips a trailing "(...)", splits the address hints off ("... on Hurston" -> body hint Hurston, system hint likewise), keeps words only, centre -> center, and inside words with a digit reads o as 0, i/l as 1 and collapses runs of 0 ("S1DCO06" = "S1DC06"). `resolveStopPlace(step, ctx)` (and `resolvePlaceText(text, ctx, marker?)` without a step) returns a `StopPlace`: text, label, the chosen roster place, the point to measure to, source (`roster` / `marker` / none), status, confidence 0-10 (same scale and colours as the WHERE AM I accuracy), the evidence in the order weighed, the top 5 candidates, `near` for marker points and `site` for generic site names (rule 41). The old chain (`stepPointWithSource`, `withNearBody`, `foldPlaceName` / `foldZeros`) is gone from the stop path; `findRosterLocation` stays for typed starts and uses `placeKey`.
35. **The game's own data first.** The objective's marker (`step.position`) is ground truth for the position; the text names the place. The marker belongs to the step's own objective place, so while a combined step's pickup is open (`stepIsPickup`) the active place has no marker (rule 30). `placeSteps` stores the marker position for every step whose objective has one (not only steps without a UEX place), since it is evidence now; "learned" is reported only when the stop's status is `marker`.
36. **Evidence adds up.** For each roster place (two spellings of one place = one candidate, the one with coordinates): name equal +6 (`exact`), same `placeKey` +5 (`corrected`), whole-word containment either way +3, a shared distinctive token (has a digit, 4+ chars) +2; no name points -> not a candidate. Body hint equal +2, different -6; system hint equal +1, different -6. Marker (Settings "marker distance" on, marker known): within 2 km +4, 2-10 km 0, over 10 km -5. A start that came from a read (not typed) within 1 km: +2 ("you are here").
37. **One answer, or "not sure".** The top candidate with coordinates wins when it scores 5+ and beats the runner-up by 3+: status `exact`, `corrected`, or `guess` (confidence = score, max 10; guess -2). A winner over 10 km from the marker -> `mismatch`: the marker point is used, confidence 4, the raw text shown. No winner and a marker -> `marker` (body/system and `near` from the nearest roster place within 25 km, confidence 8). No winner and no marker: candidates tied at 5+ -> `unsure` (no distance, confidence 2), otherwise `none` (no distance, confidence 0). A look-alike name on another body loses its points (-6) and is never measured.
38. **Every screen shows how sure it is.** A small tag (`MatchTag`) follows the stop's place on the overlay header, each Next row/group and the Jobs step: "✓ exact", "≈ corrected", "📍 game marker", "? guess", "⚠ mismatch", "? not sure", "✗ not found", coloured from the confidence like the accuracy tag; its tooltip lists the evidence. Exact and marker look normal; the others are amber or red. `mismatch` and `unsure` rows add the candidates line "not sure: A or B?".
39. **Diagnostics show the reasoning.** SNAPSHOT distance-table rows carry `match` (the StopPlace with the chosen place as name and coordinates only); `other.matches` lists every open stop that isn't `exact` (text, status, confidence, evidence, candidates) and prints as `## MATCHES` right after `## SNAPSHOT`, "(all exact)" when there are none.
41. **Generic sites belong to the contract's named place (user, mid-batch 7).** Generic site names ("Security Compound", "Storehouse", ...) are not UEX places; the stop belongs to the named place the contract mentions. When the active text gets no name candidate, the resolver looks for the parent: first a roster place named elsewhere in the same step or job (label, pickup place, the job's other steps; scored the same way, must win clearly) within 25 km of the marker (or with no marker), `site.from = 'contract'`; else the nearest roster place within 25 km of the marker, `site.from = 'marker'` (`near` is the same object). With a marker the position is the marker (status `marker`, confidence 8, `site.meters` = marker -> parent). With no marker but a contract parent, the parent's coordinates are used (status `guess`, confidence 5, evidence "no game marker: using <place>, named in the contract"). Never a different place's distance. Shown as "Security Compound · at Covalex Distribution Centre S1DC06", plus " (4 km)" when the site came from the marker and is over 1 km away. The route may group a site with its parent when they are within 1 km. Cases: J82's drop-off "Security Compound" -> Covalex S1DC06 from the contract; J74's -> HDPC-Cassillo from the marker (the contract's HDPC-Farnesway is not within 25 km of the marker).
40. **Real cases are a table.** `test/replay/fixtures/stop_cases.json` holds every distinct stop text from the user's exports plus the J74 and J82 cases, each with its expected answer; `test/replay/resolve_checks.mjs` runs the whole table and a check per scoring and decision rule. A new place problem = a new row; every change must pass the whole table. The app replay checks are `match-j82-corrected`, `match-j82-dropoff-site`, `match-j74-marker`, `match-lookalike-other-body`, `match-two-equal` and `match-all-exact` in `test/replay/replay.mjs`.

Known limits: a body's radius is estimated from its places, so a body with few or no roster places can't be matched (the local planet table, userData/other-bodies.json, uses the panel's exact `Radius:` once WHERE AM I has read it near that body). A marker on a body with no place within 10 km of it stays uncalibrated, and its step still shows "Not found in UEX".

Options for these behaviours live in Settings (Other block); defaults in `OTHER_SETTING_DEFAULTS` (`src/other/workMode.ts`).

**Images are opt-in** (tick box off by default): "Include images (OCR crops and an overlay picture). Pictures can't be cleaned of names." When ticked, the last zone 1 and zone 2 crops (unscaled, from the last WHERE AM I capture) and a `capturePage()` picture of the overlay window are saved next to the export as `<export base>-zone1.png`, `-zone2.png`, `-overlay.png`, listed under `## IMAGES` and in the export result; all of them are also stitched side by side into `<export base>-all.png` (`combinedImage` in the result; COPY IMAGES copies it, rule 33). Pictures are not sanitised: they can show the player's handle or other players' names, so check them before sharing.

The diagnostics trace (EXPORT DIAGNOSTICS) adds `trace(...)` calls to upstream Haul files: `src/main/logWatcher.ts`, `src/main/scanLog.ts`, `src/main/ocr/index.ts`, `src/main/contractData.ts`, `src/renderer/src/state/store.ts` (edit actions wrapped in a pass-through that records the action), `src/renderer/src/state/route.ts`. They change no behaviour; after an upstream merge, re-add them or drop them (the export still works, with less Haul detail).
