## Job rules (user, 2026-10-14)

These are the intended behaviour of Other mode. Change them only with the user.

1. **Haul mode is only for hauling.** In Haul mode the Other side ignores every contract; it never creates jobs.
2. **Two outcomes:** completed or abandoned. Fail, Abandon and "Player left" all count as abandoned; the reason is not shown.
3. **The latest ending wins.** Endings in the log (EndMission Complete / Fail / Abandon) mark the job automatically during play.
4. **Re-share reactivates.** A new "Contract Accepted" for a mission id makes its job active again, even if it was archived (a party member re-shared it after you left).
5. **Quitting ends contracts.** "Player requested disconnect" (quit to menu, server hop) and `<SystemQuit>` with `Quit via console command` or `User closed the application` (quit game) mark every active log job abandoned.
6. **A crash keeps jobs.** No ending is inferred from missing contracts: not at app start-up, not from a new Game.log, not from a log scan. After a crash you rejoin with your contracts, so jobs stay active until the log ends them or you do.
7. **Start-up replays only new log events** (after `lastLogEventAt` + `lastLogEventCount`, so nothing is applied twice): the previous log in `logbackups` when newer than the watermark, then the current Game.log. A previous log that ends with SystemQuit applies rule 5; one that ends without it is a crash (rule 6). REFRESH (rule 26) is the only re-read that ignores the watermark, and it applies markers only.
8. **One window owns Other.** Only the main window applies log events and saves; the overlay shows the same jobs, sends its button presses (step done, complete, abandon) to the main window, and reloads when the main window saves.

## Where the player is (user, 2026-10-14)

9. **One `where` field.** The jobs doc (`other-jobs.json`) keeps the player's position as `where: Where | null` (`src/other/otherWhere.ts`: name, label, point, system, body, `source`, `at`). It replaces the old `currentLocation` / `currentLocationAt`. Sources:
   - `tick`: you tick a step DONE / GO HERE / TURN IN → that step's place (read before the tick changes the active step);
   - `objective`: an Objective Complete line in the log ticks a step → that step's place, at the log time;
   - `inventory`: the log's RequestLocationInventory / Update Inventory Location events (a "left the place" event clears `where` only when the current `where` came from `inventory`);
   - `map` / `displayinfo`: WHERE AM I (rule 11);
   - `typed`: the STARTING AT box (stored separately as `startLocation` + `startTypedAt`).
   Quantum and ATC lines are **not** a source: no log line names the place (checked against real logs). The UI shows which source the start came from.
10. **STARTING AT mode** (`otherStartMode`, AUTO / FIXED toggle on the start line). **auto** (default): the newest of the typed start (`startTypedAt`) and the latest clue (`where.at`) wins. **fixed**: the typed start only; empty means no start. A non-typed start older than 5 minutes shows as stale.
11. **WHERE AM I** reads the star map: hotkey `otherWhereHotkey` (default Ctrl+Shift+L) or the one button on the overlay card's start line. The start line (FROM, ACC, match tag, 📍, the WHERE AM I notes, "No start") sits at the bottom of the card, under GO HERE / ABANDON / AFK with a gap of about 12 px and above the SUPERCARGO label, and the 📍 has a click area of at least 24x24 px, so a click meant for the pin can't land on a button (user, 2026-10-14, option A; R1 1.0.1). One screenshot, two zones: zone 2 (r_DisplayInfo 3 text, upper right) first when `otherWhereUseZone2`, then zone 1 (the map's bottom location line) as fallback. The result is broadcast to every window; only the main window applies it (`applyWhere`) and saves. A failed read (hotkey or button) shows "couldn't read the map, try again" and changes nothing; a second run while one is running returns busy.
12. **Location never touches the log watermark.** `where` updates (from any source, including WHERE AM I) never change `lastLogEventAt` / `lastLogEventCount`; only log job events advance them (rule 7).
13. **Distances are system-aware.** A stop in another system goes via the gateway ("38.0 Gm + 1 jump"); stops sort by jumps, then metres. Two points on the same planet or moon are measured over the surface ("≈490 km surface").

14. **Position accuracy (0-10).** Every clue carries `where.accuracy`, set when it is taken (`ACCURACY` in `otherWhere.ts`): display info near a body 10, display info in space 9, map line naming a place 8, inventory 7, objective 6, tick 5, map line naming only a body 4, map coordinates only 3. A typed start has no score (it is the user's choice). The overlay start line shows a coloured `ACC n` tag with a 10-segment bar; the Next tab shows the score and its word (exact 10-9, good 8-6, rough 5-4, guess 3-1, none 0) on a small red-orange-green slider under STARTING AT. Number and word are always shown, so colour is never the only signal.
15. **Fading.** The score drops by 1 for every 5 minutes since `where.at`, never below 1 (`whereAccuracy()`). A display-info read whose ServerTime differs from the PC clock by more than 2 minutes is "maybe stale": −3 (min 1), noted in its checks and diagnostics.
16. **The whole panel is read.** Zone 2 reads the whole r_DisplayInfo panel and uses, best first, the planet zone line or CamPos + the body centre (near a body), then the SolarSystem line (checked against Root; in space only, rule 32), then zone 1, each only when its sense checks pass (recorded in `checks`). A read with no system named is still OK. **Naming order** (user, 2026-10-14: "Open space should be when not in any of these situations"): the read names the place, first that applies: 1 station — the panel's "Current player location : … (LZ : RR_CRU_LEO)" code, or a hangar / rest-stop / station zone, maps through the site-code table to a station ("Seraphim Station (hangar)" in a hangar, else "Seraphim Station"); 2 POI — the code or zone maps to an outpost, landing zone or site ("<name> · <body>"); 3 planet — within 100 km of a body, as before ("Hurston · N km up"); 4 "Open space" only when none of these apply. A place the position already names in range keeps its label exactly ("HDRSO-Stott · 22.8 km", "Covalex Distribution Centre S1DC06 · 305 m"): the code/zone naming only replaces the planet ("<body> · N km up") or "Open space" wording. Distances still use the panel's exact position; an unknown code falls back to the old wording. The naming is recorded in `checks`, and `where.placeKind` says which step named it. After every WHERE AM I read the overlay shows a short note for about 4 s ("Read OK · display info · ACC 10", "Panel unreadable → used map line · ACC 3", or the failure message; the previous start is kept on failure).
17. **Live reads** (`otherWhereLive`, off by default; `otherWhereLiveSec` 45, 30-120): the main process re-reads zone 2 only, every N seconds, with no keypress; it skips while a read is running or a hotkey is being recorded. Only good reads change `where`; live reads are silent, except one quiet message after 3 failures in a row. Diagnostics count them.
18. **Tracked mission.** The panel's `Tracked mission : <name> [<uuid>]` line marks the active job whose mission id starts with the same first 8 hex characters (O/0 and I/1 tolerated) as `trackedMissionId` in the doc. The overlay shows a TRACKED tag on that job and jumps the card to its next stop when a new tracked id arrives; the Next tab shows the tag too.
19. **AFK button** (overlay, next to TURN IN / ABANDON; Windows only). Click to start, click again to stop; while on it is amber with "AFK ON · next key in N s". Every `otherAfkIntervalSec` (15 s) it brings the Star Citizen window to the front and presses `otherAfkFirstKey` (F2, the map) on the first cycle, then `otherAfkCycleKey` (F1) each later cycle, as scan codes through Windows SendInput (a PowerShell helper; no native module). It stops on the button, when the game window is gone, after `otherAfkMaxMin` (120; 0 = no limit), or when the app quits, and leaves the game focused. AFK takes no WHERE AM I reads (user, 2026-10-15, batch 13: "afk reads, can go away period."): the once-a-minute read and the setting `otherAfkWhereRead` are gone; an old saved value is ignored (no migration). On other systems Start returns "Windows only". The settings hint says: "Presses keys in Star Citizen for you. Check RSI's terms before using it; the game window is brought to the front every cycle." Test seam: `SC_AFK_DRYRUN=1` sends no focus or keys and only records the presses (`presses`, `lastKeys`); `SC_AFK_INTERVAL_MS` sets the interval in a dry run.
20. **Hotkey recorder.** Both global hotkeys (OCR capture and WHERE AM I) are set by clicking the field and pressing the combination ("Press keys…"); Esc cancels, Backspace/Delete clears (off). A combination needs Ctrl, Shift or Alt unless it is F1-F24; modifier-only presses are ignored. While recording, all app global hotkeys are paused. It warns about a clash with the other hotkey or Ctrl+Shift+D (debug), and after saving shows "in use by another app" when registration fails.

## Places from mission markers (user, 2026-10-14)

21. **Body-frame markers.** A mission marker (`CLocalMissionPhaseMarker::CreateMarker`) gives a position in its zone's frame. A zone is calibrated as before (root zone, small zone, or a z-match with a UEX place). When it isn't, and the marker is not root or small, the zone may be a planet or moon's own frame: each body's radius is estimated as the median distance of its roster places (`Location.body`) from its centre (the roster entry named after the body); the candidates are bodies whose radius is within ±3% of |position|; for each, centre + position must land within 10 km of one of that body's places. Exactly one body passing → the zone is calibrated with that body's centre (method `body`, the near place recorded). None, or more than one (Hurston and microTech are both ~1000 km), → the zone stays uncalibrated and the decide trace says why. Calibration uses the merged roster (Haul + Other places, `mergeLocations`).
22. **Generic place names say where they are.** A step whose place isn't in UEX ("Security Compound") but whose point came from a marker carries `near` = the nearest roster place within 25 km. The overlay start/stop line and the Next tab show "Security Compound · near HDPC-Cassillo (4 km)" with the distance, instead of "Not found in UEX". A step whose pickup is still open is measured from its pickup place, never from its marker (rule 30).
23. **Zone tables are per server.** Zone ids change with every server (the same SolarSystem has a different id the next session), so the marker zone table for the current build is cleared on a new session line ("Log started") and on a disconnect or quit. Markers after that are calibrated fresh. Positions already placed on steps (system frame) stay. The decide trace records `marker zones reset: session` / `disconnect` / `quit` with the number of zones dropped.
24. **Pickup before delivery.** The next open step, and the step order the Next tab uses (show-all and route), put an open pickup before the open turn-in / delivery steps of the same job that carry the same item (case-insensitive), even when the game lists the delivery first. If either side has no item, game order is kept. Combined "collect from A, deliver to B" steps (`pickupLocation`) are unaffected. The saved steps keep game order.
25. **Export diagnostics copies to the clipboard.** After a successful save from the Settings or Debug button, the main process puts the whole saved text on the clipboard. The result line reads "Saved and copied · 1.4 MB · <path>", adding " (large: attaching the file may work better)" above 1 MB, or "Saved (copy to clipboard failed)". The `--export-diagnostics` command line never touches the clipboard.

## REFRESH (user, 2026-10-14)

26. **REFRESH re-reads markers for active jobs.** The REFRESH button (Next screen next to STARTING AT, Jobs screen header; not on the overlay) does three things: (1) main re-pulls the Other places roster (`otherPlaces:refresh`) and the renderer reloads it, so views recompute; (2) main re-reads the same files as the start-up scan (newest `logbackups` file, then Game.log) **ignoring the watermark**, and returns only `marker` events whose mission id is in the given list of active jobs, plus `session` lines for the build and zone context, in log order (`otherJobs:refreshScan`, `scanMarkersFor()`); nothing else (no accepts, objectives, endings, quits); (3) the main window empties the current build's zone table, calibrates again from those markers (`calibrateZone`, including the body-frame path) and re-places steps over all jobs. Why: marker lines are written when the contract is accepted, so after a restart the start-up scan (rule 7) never shows them again, and a step that a newer build could place (rule 21) stayed "Not found in UEX" (the user's J74).
27. **REFRESH never moves the watermark or revives jobs.** It does not change `lastLogEventAt` / `lastLogEventCount`, job status, steps' done flags, history, and never creates or ends a job; an ended job's markers are not read (only active mission ids are sent). Only the main window applies it (rule 8); the overlay has no button. The result shows on the screen for about 6 s and goes to the decide trace (`refresh`) and the debug log: "Refreshed · 1 job · 1 place found (Security Compound near HDPC-Cassillo)" or "Refreshed · nothing new" (counts: active jobs, markers read, steps that gained a position, zone result).
28. **Automatic once per version.** On the first start after an update (app version + git commit from DebugInfo differs from the doc's `refreshedForVersion`), steps 1-3 run silently after the start-up scan and the doc stores `refreshedForVersion`. Later starts of the same version don't run it (decide trace `auto refresh: new version`, once).

## Pickup distance and bad reads (batch 6, user 2026-10-14)

The case: standing at Covalex Distribution Centre S1DC06 (Hurston), job J82's combined step "Collect Scrap from Covalex Distribution Center S1DCO06 on Hurston. Deliver Scrap to Security Compound" (OCR doubled O) showed "≈4 km" and "near Covalex S1DC06 (4 km)": the pickup name matched nothing, so the row used the step's marker, which is the drop-off (Security Compound, ~4 km away). Two reads at the same spot said "Open space" and one said "Rappel · 46.4 km".

29. **OCR doubled zeros.** (Batch 7: folded into `placeKey`, rule 34. Batch 9: `findRosterLocation` / `explainPlaceLookup` are gone; every lookup is the resolver, rules 61-68.) Place lookup (`findRosterLocation`, `explainPlaceLookup`) tries, after exact and contains, a last tier on folded names with runs of two or more zeros collapsed to one inside words that carry a digit ("S1DCO06" = "S1DC06"), exact match only, with the same pick rules (coordinates first, address system). The lookup explains it as method `folded`.
30. **A pickup is measured from the pickup place.** (Batch 7: kept by the resolver, rule 35: a pickup has no marker.) While a step's pickup is open (`stepIsPickup`), its distance and `near` come only from the pickup place; the step's `position` (the marker) is never used, because on a combined collect-and-deliver step the marker sits on the delivery place. A pickup place that can't be found gives no distance (the row's no-distance text), not the drop-off's. After the pickup is done, the marker is used as before (rule 22).
31. **Unknown system names are not systems.** In display-info reads, `knownSystem()` returns '' for a name that is not a known system (garbled reads such as "Zone", "Zope"), so the read has no system rather than a made-up one; the map line keeps its title-cased name. Near a body, the body is looked up in the read system's places first, then in every system (a misread system name).
32. **Near a body, never the star-frame lines.** When the panel says the player is near a body (planet zone line or CamPos) but the body position fails (no body, or a failed check), the read gives no position: the SolarSystem / Root lines turn with the planet and don't match roster places. Its checks record `position: near <body> but the body position failed: star-frame lines not used on a planet`, and the previous start is kept (rule 16). In space the SolarSystem / Root path works as before. A read with a position is then named in the rule 16 order (station, POI, planet, open space); "Open space" is the last step, never the default when the panel names a station or POI.
33. **COPY TEXT / COPY IMAGES.** After a successful export from Settings or Debug, a COPY TEXT button (and COPY IMAGES, only when pictures were saved) sits next to the result line. COPY TEXT reads the last saved `.txt` back and puts it on the clipboard ("Text copied · 1.1 MB"); COPY IMAGES puts one picture on the clipboard: every saved picture side by side, top-aligned, 16 px black gaps, unscaled, saved next to the export as `<base>-all.png` and listed in `## IMAGES` as "saved: <base>-all.png (all pictures in one)" ("Picture copied (3 in one)"). Feedback shows for about 4 s; before any export both answer "no export yet". The automatic text copy on export (rule 25) stays.

## One stop-place resolver (batch 7, user 2026-10-14)

Why: a stop's place used to be found by a chain of rules (exact, contains, O/0 fold, zero fold, marker fallback, nearest place, pickup exception); each fix added a link and the links interacted (the J82 pickup got the drop-off's 4 km). One resolver now weighs all the evidence and returns one answer per stop, read by every screen, the route sort and diagnostics.

34. **One normaliser, one resolver.** `src/other/otherResolve.ts` (pure): `placeKey(text)` lower-cases, strips a trailing "(...)", splits the address hints off ("... on Hurston" -> body hint Hurston, system hint likewise), keeps words only, centre -> center, and inside words with a digit reads o as 0, i/l as 1 and collapses runs of 0 ("S1DCO06" = "S1DC06"). `resolveStopPlace(step, ctx)` (and `resolvePlaceText(text, ctx, marker?)` without a step) returns a `StopPlace`: text, label, the chosen roster place, the point to measure to, source (`roster` / `marker` / none), status, confidence 0-10 (same scale and colours as the WHERE AM I accuracy), the evidence in the order weighed, the top 5 candidates, `near` for marker points and `site` for generic site names (rule 41). The old chain (`stepPointWithSource`, `withNearBody`, `foldPlaceName` / `foldZeros`) is gone from the stop path; `findRosterLocation` stays for typed starts and uses `placeKey`. (Batch 9: `findRosterLocation` is gone; typed starts and every other lookup use the same resolver, rules 61-68.)
35. **The game's own data first.** The objective's marker (`step.position`) is ground truth for the position; the text names the place. The marker belongs to the step's own objective place, so while a combined step's pickup is open (`stepIsPickup`) the active place has no marker (rule 30). `placeSteps` stores the marker position for every step whose objective has one (not only steps without a UEX place), since it is evidence now; "learned" is reported only when the stop's status is `marker`.
36. **Evidence adds up.** For each roster place (two spellings of one place = one candidate, the one with coordinates): name equal +6 (`exact`), same `placeKey` +5 (`corrected`), whole-word containment either way +3, a shared distinctive token (has a digit, 4+ chars) +2; no name points -> not a candidate. Body hint equal +2, different -6; system hint equal +1, different -6. Marker (Settings "marker distance" on, marker known): within 2 km +4, 2-10 km 0, over 10 km -5. A start that came from a read (not typed) within 1 km: +2 ("you are here").
37. **One answer, or "not sure".** The top candidate with coordinates wins when it scores 5+ and beats the runner-up by 3+: status `exact`, `corrected`, or `guess` (confidence = score, max 10; guess -2). A winner over 10 km from the marker -> `mismatch`: the marker point is used, confidence 4, the raw text shown. No winner and a marker -> `marker` (body/system and `near` from the nearest roster place within 25 km, confidence 8). No winner and no marker: candidates tied at 5+ -> `unsure` (no distance, confidence 2), otherwise `none` (no distance, confidence 0). A look-alike name on another body loses its points (-6) and is never measured.
38. **Every screen shows how sure it is.** A small tag (`MatchTag`) follows the stop's place on the overlay header, each Next row/group and the Jobs step: "✓ exact", "≈ corrected", "📍 game marker", "? guess", "⚠ mismatch", "? not sure", "✗ not found", coloured from the confidence like the accuracy tag; its tooltip lists the evidence. Exact and marker look normal; the others are amber or red. `mismatch` and `unsure` rows add the candidates line "not sure: A or B?". **Problem stops stand out (user, 2026-10-14).** One shared rule, `src/other/renderer/stopIssue.ts` (`stopIssue`, `worstIssue`, `issueRowStyle`, `issueTextStyle`): match status `none` is red ("no place" when the step has no location, else "not found"); `guess`, `unsure` and `mismatch` are amber; every other status is fine. The Jobs tab (each step row, and the collapsed job row with a chip "✗ N step(s) need a place" when any is red, else "? N step(s) to check"), Next tab rows/groups and Learned Data "Needs your eye" rows get a light tinted row with a left stripe in that colour; the overlay tints only the words (the place name, the objective text and the "Next Location" place words), never the card; the SCAN CONTRACT confirm screen tints its "→ place" words the same way (words only). The `MatchTag` stays the chip and still opens the fix panel. The fix panel opened from a tag belongs to that stop (or start): it closes when the card or the start changes, so a pick can never be saved against another stop (2026-10-14).
39. **Diagnostics show the reasoning.** SNAPSHOT distance-table rows carry `match` (the StopPlace with the chosen place as name and coordinates only); `other.matches` lists every open stop that isn't `exact` (text, status, confidence, evidence, candidates) and prints as `## MATCHES` right after `## SNAPSHOT`, "(all exact)" when there are none.
41. **Generic sites belong to the contract's named place (user, mid-batch 7).** Generic site names ("Security Compound", "Storehouse", ...) are not UEX places; the stop belongs to the named place the contract mentions. When the active text gets no name candidate, the resolver looks for the parent: first a roster place named elsewhere in the same step or job (label, pickup place, the job's other steps; scored the same way, must win clearly) within 25 km of the marker (or with no marker), `site.from = 'contract'`; else the nearest roster place within 25 km of the marker, `site.from = 'marker'` (`near` is the same object). With a marker the position is the marker (status `marker`, confidence 8, `site.meters` = marker -> parent). With no marker but a contract parent, the parent's coordinates are used (status `guess`, confidence 5, evidence "no game marker: using <place>, named in the contract"). Never a different place's distance. Shown as "Security Compound · at Covalex Distribution Centre S1DC06", plus " (4 km)" when the site came from the marker and is over 1 km away. The route may group a site with its parent when they are within 1 km. Cases: J82's drop-off "Security Compound" -> Covalex S1DC06 from the contract; J74's -> HDPC-Cassillo from the marker (the contract's HDPC-Farnesway is not within 25 km of the marker).

## Match memory (batch 8, user 2026-10-14)

Why: the resolver (rules 34-41) decides each stop's place from the text alone, every time. A stop it gets wrong or can't decide ("? not sure") stays wrong until the text changes. The app now remembers what it saw, what the game proved and what you set, in `<data folder>/other-matches.json` (`src/other/otherMemory.ts`, pure; main owns the file: `src/other/main/matchMemory.ts`).

42. **Match log.** Every open stop that isn't an exact match is remembered locally: text, chosen place, status, confidence, last evidence (max 8 lines); seeing it again bumps `seen`. Only the main window reports (debounced 5 s); the overlay never does. Generic sites are keyed with the place the contract names (`memoryKey(text, context)`). At most 500 entries: the oldest `lastAt` goes first, a `user` entry is never dropped. Seeing a stop again never changes a place you set.
43. **Proof from the game.** When the log's Objective Complete ticks a step, and the latest position read (`where.source` `displayinfo`, `map` or `inventory`, accuracy 7 or more, within 10 minutes of the line's time) shows where you were: the chosen place within 1.5 km of that point (or the inventory clue names the chosen place) counts `confirmed` +1; otherwise `wrong` +1, keeping where you were (nearest roster place and metres; last 3). No read near the line's time: no proof either way. The read is taken before the completion moves `where` to the step's place.
44. **Learned names.** A game entry with `confirmed` 2 or more and more confirmations than wrongs adds +4 to its place ("learned: game confirmed ×N"); if that place then wins, the status is `learned` ("✓ learned"). `wrong` 2 or more on a place takes −4 from it ("the game showed this was wrong ×N").
45. **Fix it on the stop.** The match tag on the overlay, the Next tab and the Jobs step is a button. It opens a small panel with the evidence lines and: ✓ Right (sets a `user` entry for the place shown), ✗ Wrong → pick (search the merged roster, the runner-up candidates listed first, at most 30 shown; sets a `user` entry), Forget (only when an entry exists). The change applies at once in every window. Esc or a click outside closes it.
46. **You win.** A `user` entry whose place has coordinates decides the stop outright: status `user` ("✓ you set"), confidence 10, first evidence line "you set this ✓". For a generic site your place becomes the site (from `contract`); the game's marker still gives the point when there is one.
47. **Flagged, never overridden.** When game proofs say `wrong` 2 or more for a place you set, the entry is `disputed`: your place still wins (confidence 6, "you set this; ⚠ the game disagrees ×N") and the tag and list show "⚠ the game disagrees" in amber with where you actually were ("you were at X"). Nothing changes your place silently; you fix or forget it.
48. **Learned places list.** The LEARNED DATA tab, Places section (rules 74-80; Settings → OTHER MODE → LEARNED PLACES until batch 11): table text → place, how it was learned ("you set it", "game confirmed ×N", "unproven", "⚠ the game disagrees"), last used; Change (same picker) and Forget per row; a search box; a filter (all / you set / game / disputed).
49. **Undo.** Every change (new entry seen, set, forget, game proof, undo) keeps its before and after; the last 50 are kept, newest first, under RECENT CHANGES on the LEARNED DATA tab, each with Undo (restores the before; a new entry undone is removed). Diagnostics export `## MATCH MEMORY`: the entries (disputed first, then yours, then the game's by last use) and the last 50 changes.

53. **OCR look-alikes count as the same name.** After the `placeKey`-equal tier (rule 36) the resolver compares confusion-folded keys: inside words with a digit S↔5, B↔8, Z↔2, G↔6 (with O/0 and I/l/1 as before); in every word rn→m, vv→w, cl→d and `|`→l. Equal folded keys are `corrected`, +5 ("≈ corrected").
54. **Close spelling.** Then a weighted Damerau-Levenshtein similarity on the folded keys (confusion pairs cost 0.3, other edits 1): 0.9 or more with a key of 8+ characters +4 ("close spelling: <name>"), 0.82-0.9 +3. Code words (a digit and letters: S1DC06, CRU-L5, SAL-2) must be equal after folding or the place gets no spelling points (S1DC06 never matches S4DC05). The usual decision rule (rule 37) still applies, so a close spelling alone with a rival is "? not sure", never a wrong place.

    and `exports/` (default folder of the diagnostics and run-export save dialogs). These known names are the
    "SuperCargo files"; `holdsData(dir)` is true only when one of the SuperCargo files (not just a folder such as logs, exports, outbox or game-data) is in that folder's root (Q6, 2026-10-14). `settings.json` is never
    one of them (never moved, never copied). `settings.json` is always in the default folder
    (`settingsFile()`), so a moved folder can be found. Large re-downloadable caches (`tessdata/`, `ocr-model/`) and
    Chromium's own files stay in Electron's userData (`cachePath()`).
82. **Fresh start.** Nothing is read from, moved out of or deleted in the old `%APPDATA%\SuperCargo` folder.
83. **Moving it.** Settings → GENERAL → DATA FOLDER (`DataFolderRow.tsx`) shows the folder ("default", or the fallback
    reason) with CHANGE…, OPEN FOLDER and RESET TO DEFAULT. CHANGE… uses the picked folder AS IS (no subfolder is made).
    No SuperCargo files there: the current data is copied in first (never overwriting a file). SuperCargo files there:
    `checkDataFolder()`; fine: used as is; damaged: nothing is saved and the row shows an inline warning listing the
    files and reasons with RESET AND CONTINUE / CANCEL. RESET AND CONTINUE (`dataFolder:repair`) runs
    `moveForRepair(target)`, then copies the current data in ("Moved the old files to <folder>. Copied N files.").
    CANCEL keeps the old folder. On success `settings.dataFolder` is saved and the app asks for a restart (RESTART NOW);
    the change takes effect on the next start. IPC `dataFolder:get / :choose / :reset / :open / :restart / :repair`
    (`src/main/dataFolderIpc.ts`).
84. **Fallback.** A chosen folder that can't be used at start (missing drive, no write access) is not used: the app runs
    on the default folder and DATA FOLDER shows why (`dataFolderStatus().fallback`).
85. **Releases.** Version line R1, app semver `1.0.0`. Windows: `SuperCargo-OtherModes-R1-<ver>-Setup.exe` (per-user
    NSIS, no admin, install folder can be changed, desktop shortcut optional and unticked, the choice kept on silent
    updates, uninstall never touches user data; updates itself after asking) and
    `SuperCargo-OtherModes-R1-<ver>-Portable.zip` (never downloads; the update window offers Open Release Page). Built
    by `.github/workflows/release-win.yml`, notes in `release-notes/<ver>.md`.
86. **Damaged data at start-up.** After app ready and before any window opens, `startupDataCheck()`
    (`src/main/dataCheck.ts`) runs `checkDataFolder(dataFolder())`: each existing SuperCargo JSON file must parse and
    have the shape its loader expects (for example `history.json` `{ entries: [] }`). Any problem shows a native
    warning "SuperCargo data can't be read" listing the files and reasons, with "Reset and continue" / "Quit" (Quit is
    the default and the cancel button). Reset: `moveForRepair()` moves ALL SuperCargo files and folders (not only the
    damaged ones; not `settings.json`, not `Moved for Repair`) into `<folder>\Moved for Repair\<YYYY-MM-DD HH-MM>\`
    keeping the folder structure (" (2)", " (3)"… on a clash), logs what moved, and the app starts with empty data.
    Quit: the app quits and changes nothing. A chosen folder that is missing at start still falls back (rule 84).
87. **Updates like Gremlin.** `src/main/updater.ts` checks once at start-up when `autoCheckUpdates` (default ON, label
    "Check for updates at start-up") and whenever Settings → GENERAL → UPDATES → CHECK FOR UPDATES is pressed. No
    hourly recheck; no automatic download (`autoDownload` and `autoInstallOnAppQuit` off). Prerelease versions skip
    checks. States (`UpdateState`): checking, upToDate, available, downloading, ready, error, failed.
88. **The Check for Updates window** (`UpdateWindow.tsx`, modal). Opens by itself when the start-up check finds a
    version that isn't skipped; stays quiet at start-up for skipped / up to date / error. Available: "R1 <new> is
    available. You have R1 <cur>." with the notes and Update Now / Skip This Version / Later (portable: Open Release
    Page / Skip This Version / Later). Update Now: progress bar ("Downloading… 12.3 / 85.0 MB") with a Cancel button; Cancel or closing the window
    during the download cancels it and the offer shows again (like Gremlin, Q2 2026-10-14), then electron-updater
    checks size and sha512 from `latest.yml`; ready: "Downloaded and checked. Install and Restart to finish." (Install
    and Restart / Later; Later leaves a small "Update ready — INSTALL AND RESTART" bar). A failed check of the download
    is "The download failed: <msg>" with Try Again / Open Release Page / Close; a failed check for updates is
    "Couldn't check for updates: <msg>" with Try Again / Close.
89. **What's new.** `src/main/releaseNotes.ts` reads the GitHub releases of `swill008/SuperCargo-All` (10 s timeout)
    and keeps every version newer than the running one up to the offered one, newest first; from each body only the
    text under "## What's new in R1 <ver>" (or "## What's new in <ver>") up to the next heading. Fetched before
    "available" is sent and kept for the session. Several versions: each starts with a small muted "What's new in R1
    <v>" line. Markdown is rendered as React elements (headings, bullets, bold), never as raw HTML. No notes: "Release
    notes unavailable."; the "Full release notes on GitHub ↗" link and updating still work.
90. **Skip This Version** saves `settings.skippedUpdateVersion`. The start-up check stays quiet for that version;
    CHECK FOR UPDATES by hand still shows it; a newer version is offered as normal.
91. **Updated notice.** At start-up, when `settings.lastRunVersion` is set and older than the running version, the app
    shows once "Updated — now R1 <ver>" with WHAT'S NEW (release page) and a close X; then `lastRunVersion` is saved.
92. **Reference data status.** The ships, locations, commodities, cargo grids and contract box sizes still come from
    the original SuperCargo author's repo (`AquatikJustice/SuperCargo` main `data/uex`, checked by `hashes.json`).
    Every check records per file: up to date / updated / couldn't download / fingerprint didn't match (kept the old
    copy) / format not understood (kept the old copy), with the time and a detail, in
    `reference-data-status.json`; an unreachable list marks every file "couldn't download". Failures log a warning per
    file. The update window's bottom panel (`RefDataStatus.tsx`) lists the files, "Last checked …", the source line
    and CHECK NOW; Settings → UPDATES shows "⚠ Reference data: <n> file(s) couldn't be updated — see Check for
    Updates" when any file failed. Diagnostics export a `REFERENCE DATA` section. Test seam: `SC_TEST_REFDATA_BASE`.
93. **Overlay stop header (O1).** The stop card header has a fixed height: line 1 is the place name on one line, cut
    with "…" (full name in a hover tooltip); line 2 is the tags and Body · System. Stepping ‹ › between stops never
    changes the card height. **Return to first stop (`overlayReturnToFirst`, default on; user, 2026-10-14).**
    OFF: the card stays on the stop you chose with ‹ › and only moves when that stop is gone (completed or
    abandoned). ON: the card goes back to stop 1 after the set seconds, and right away when the start really changes
    (its name or kind, or a different first stop in the order). Live WHERE AM I reads and job-file saves never move
    the card (the user's report: "if i went to contract 4, it keept going back to the beginnig, to 1. even with the
    setting turned off").
94. **Reputation ranges (O2).** A log reward like "[100–500 Rep]" / "[100-500 Rep]" / "[1,000 – 2,500 Rep]" gives `rep`
    = low and `repMax` = high (only when high > low), carried from the event to the job and the saved job. Every place
    Other mode shows rep reads "+<rep>–<repMax> REP" (en dash) when `repMax` is set, else "+<rep> REP" as before.
95. **Altitude from position (O3).** When the altitude read from the screen is garbled, missing or implausible, the
    start label ("Hurston · 436 km up") uses |position − body centre| − body radius (exact radius when known, estimated
    otherwise). A sane screen altitude that agrees with the computed one within the documented tolerance is kept.
96. **Release notes are written as we go (N1-N5).** Every batch commit adds its lines to `release-notes/<next
    version>.md`. `scripts/release-body.mjs` refuses notes without a "### New", "### Changed" or "### Fixed" section
    with at least one bullet, with placeholders (TODO, TBD, FIXME, "…"/"..." bullets, "<", lorem), or identical to the
    previous version's. `test/replay/run_all.mjs` runs `release_checks.mjs`, so a missing or empty file for
    `package.json`'s version fails the run. The release workflow stops before building when the tag
    `SuperCargo-OtherModes-R1-<ver>` already exists, and writes the final release body to the job summary.
